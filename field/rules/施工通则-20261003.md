## 纪律
- 只在施工令指定的工作树里改;开工先 `git rev-parse HEAD` 核基座;每次写前 `git status --short`,出现令外的陌生改动 = 并发污染,停手上报,禁顺手清掉。
- 禁 `git stash` / `amend` / `force` / `reset --hard`;不推送、不打 tag(合并、标签、推送归 C1)。
- commit:身份已设 `yirun-integrator`;信息中文,写清改了什么与为什么;**零署名尾注**(不要 Co-Authored-By、Generated 之类的行)。只 `git add` 产品码、测试、迁移;`tools/perm16/_tmp_*` 不入库。
- 迁移:只用施工令分配的号;写入 `packages/db/migrations/manifest.json` 只许追加在尾部;窄替换既有函数时先取现役函数体再改,不许整段覆盖中间迁移的改动;硬钉「当前尾条」的用例用仓内脚本同步。
- 改契约源(`packages/contracts/src`)= 同时动了导出件与后端镜像:改后必跑 build、export-json-schema、镜像一致检查,生成物随提交。
- 同一规则的多份副本(策略 / 库守卫 / 执行函数 / 前端镜像 / 契约)先列清单再动手。
- 红绿三步:先在基座上复现红 → 改 → 把改动临时去掉确认回红 → 复原转绿;每步留命令与读数。
- 真库用例以业务角色连接(非超级用户、无 BYPASSRLS);审批链类改动走真实「建单 + 逐签」命令路径,禁手写已签名数据进库。
- **前端 / 界面类改动**(owner 2026-10-03:「use opus 5.5 for frontend design and feel free to use better UI taste but generally still following the current design spec/style」):先读规范正本里的设计规范与界面文案规则、再看同类现有页面;沿用现有组件、样式变量与交互习惯,不引入新的组件库或另起一套视觉;在此之内可以改善布局、信息层级、留白、空态与文案。新页面在交回件里附截图或组件测试快照的路径。

## 1.7.10 车沉淀的施工规则(2026-10-13,C3)
1. **新阈值 / 时长 / 开关一律 env 可配,默认值不变,非法值回默认并 warn 一次,单测覆盖「合法 / 非法 / 未设」三态**(HF1 会话 7 天写死成常量,演练站想拉长只能改码,是反例)。
2. **前后端校验同源**:前端拦的规则后端必须同样拦(或反之明确不拦并写进交回)。反例:「至少保留一家适用门店」只在前端,接口可绕过,导致界面与 API 行为不一致(1.7.10 B10 vs 远端 S2)。
3. **令件 / 用例 / 章程里的接口路径与请求体只从代码、契约或 nginx 配置取**,禁凭记忆与手写(`/build-info.json` ≠ `/api/build-info`)。
4. **用例与盲测夹具造「人」必带职位 + 职级 + 凭据行三件**,造「产品」必带适用范围,造「卡」必带来源形态;缺一项都会在真实路径上被既有守卫拦下而产出假红(B05)。
5. **只改一处的热修也走:自生产标签拉树 → 单测三态 → 一名复核 → rc tag → 演练站换装 → 生产同码换装**;不因「小」跳门。
