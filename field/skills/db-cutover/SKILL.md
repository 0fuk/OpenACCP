# /db-cutover — 旧系统快照 → 新系统换库(读取 · 验真 · 研判 · 方案 · 配置 · 彩排 · 切库 · 收口)

存在理由:换库是公司级不可逆动作,每次都带一份新的旧系统导出、一套新的业务口径、一个漂移过的库结构。2026-09-21 第一次换库靠临时工具与人肉串接跑通;2026-10-08 第二次 owner 要求固化。本 skill 是固定流程与标准;程序在 `C:\VyqoAI\Yirun\部署相关\数据库导入程序`(独立仓,远端 github),两者同步迭代:流程改了改这里,规则改了改程序的快照配置,不许在对话里口头定口径。项目事实(服务器、库名、lane、台账)读 `PROJECT-PROFILE.md`。

## 0 · 铁律(任一条不满足 = 不切)
1. **终版快照 = 旧系统停写后导出的那份**;白天导的只能彩排。停写后若仍有零星写入,切后按「差量补录」走(§7),不重导。
2. **整库换,不就地改**:当晚克隆生产 → 在克隆上洗 / 清 / 灌 / 对账 → 开门前 swap;旧正库改名保留 + 切前 dump 锚,分钟级可回滚。
3. **全部以新导入为准**(owner 2026-10-08 口径):双跑期新系统里的单据 / 划扣 / 库存流水洗掉;员工 / 账号 / 权限 / 凭据 / 卡模板 / 目录版本 / 项目变更审批保留。改口径 = 改快照配置的 `wash` 段并记 owner 原话。
4. **零解释转录 + 规则落配置**:导入器不猜业务;每条业务规则(特价可赠送、适用门店只记录、无手机跳过、门店别名、关店迁移)都是快照配置里的一行,带 owner 原话与日期。
5. **幂等二遍零变化 + 逐店对账四平**(储值本金 / 赠金 / 欠款 / 通卡余;券数、卡数、次卡余额按店)是过门条件;脚本口径差必须有书面解释并被 owner 认可过,不许「大致对」。
6. **个人信息零原值**:源表格只在本机 `公司资料\` 与服务器工作目录;交回件 / 日志 / 仓库 / 信箱只放聚合数与客户号;服务器源件切完即删并记时刻。
7. **凭据不入命令行**;服务器动作只由部署线 / 凭据线按令执行;生产写只经执行令。

## 2 · 快照配置(程序仓 `snapshots/<日期>/config.json`,每期一份,只增不改旧期)
`files`(文件名 → 逻辑表)、`sheets`、`snapshotKey`、`snapshotDate`、`stores.aliases` / `stores.closed`(关店 → 承接店,客户 / 仓都按它)、`rules`(`giftableByName[]`、`applicableStores: record_only|enforce`、`phoneRequired`、`zeroPriceConsumable`)、`wash`(清旧批键、双跑期起点、洗 / 留表清单)、`inventory.codeMap`(旧编码 → CP 码来源)、`catalog.refresh`(目录文件 + 版本号不重置)、`sources[]`(多个旧系统各自的导入段)。配置里每条规则带 `owner` 与 `date` 字段。

## 3 · 每期必过的高价值检查(只留会丢钱或丢数据的)
- 快照是不是停写后导的;最晚写入时刻;停写后差量怎么补。
- 单价在导入时写死(实耗 ÷ 数量),不靠页面回退取目录价(2026-10 的 460/780 事故)。
- 被新系统划扣过的旧权益、新建客户、pending 审批:洗 / 留 / 终局三选一写进配置,逐表有数。
- 库存:旧编码换 CP 码命中率;期初无撤回命令,克隆上按批删;预警值等结存上的人工值先留档再回填。
- 切前 dump 锚 + 旧正库改名保留;切后首笔真实写入 = 回滚点失效,写进执行令。
- 个人信息:服务器源件切后删;本机源目录不入仓、不入镜像。

## 规则治理硬门(CUT1008 起,导入器 / 换库一律适用)
1. 导入器的每个取舍点(拒行、跳过、丢列、改写语义、降级)都必须登记在快照配置 rules.registry[](规则 id、类型、触发条件、决策人、日期、shownToOwner、说明),代码引用了而登记册没有 → 停。表头里的每个可选列都必须有登记规则(映射 / 丢弃 / 降级)→ 否则 inspect 停。
2. 每次 inspect / dry-run / rehearse / apply 都必须产出「未按预期导入清单」(out/未按预期导入清单-<snapshotKey>-<阶段>.xlsx + .json)并过守恒断言(每张源表:源文件行数 = 无手机跳过 + 分区后行数;分区后行数 = 写入 + 清单行数)。守恒不平 = 有行静默消失 = 红,不得继续。
3. 评估件和执行令必须附清单摘要:按 门店 × 规则 的"未导入"行数 / 金额,和"导入但有偏差"按规则的行数 / 金额,并逐条列出 registry 里 type 为 rewrite_semantics / downgrade 的规则及其 shownToOwner 状态。不附摘要,不得签发。
4. registry 里 shownToOwner=false 且 type 为 rewrite_semantics / downgrade 的规则,必须先用人话给用户逐条确认(规则 id + 说明 + 影响行数 / 金额),用户明确答复后才可改成 shownToOwner=true 并写决策人 / 日期;导入器对这类规则未确认时真 apply 会拒绝启动,不得用批量改 true 的方式绕过。主编排不得自己代用户确认。
5. 清单里 R-REJ-* / R-SKIP-* 按店出现异常偏高的行数或金额,先出处置方案(补目录 / 补导出 / 用户裁),再谈签发。
6. 切库后 reconcile 必须带三项新核对:逐店卡数(客户 + 卡名)、逐卡项目剩余次数(源 JSON 的 cardLedger)、通卡池次数 / 剩余金额;任何一项不平不得收口。

教训来源:CUT1008(2026-10-08 换库)导入器把次卡 / 套餐卡 / 时间卡建成「期初载体」且不写卡名、通卡零权益、「上宾|上雅」正则误伤 18 项目,门店切后当天发现,用户定性 P0(「凭什么乱改规则」)。根治 = 1.7.4 车 + 本节硬门。
